# GUARDRAILS: AutoPkg Recipe Development (vendor-drop + stable-URL)

## Task Description
Write, debug, and validate AutoPkg recipes for your org's software packaging pipeline
(Acme Fruit Co. in this kit's examples) — primarily Pattern 4 (vendor-drop,
locally-cached installer, no download URL) and Pattern 5 (stable-URL pkg). In a
typical setup, output feeds a CI job → deployment pipeline → MDM (e.g. Jamf),
ultimately deployed to the org's managed Mac fleet.

## Audience & Blast Radius
Recipes are PR-reviewed before merge, but once merged they build packages deployed
fleet-wide via Jamf. Wrong output isn't instantly destructive (there's a human review
gate) but a recipe that builds "successfully" with wrong content could ship broken or
unintended software org-wide. Internal tooling, not customer-facing.

## Repeatability
Recurring, not one-shot. Each batch covers several vendor apps sharing one of five
recipe patterns; the patterns repeat, the specific vendor files don't.

## Environment
macOS required — `autopkg`, `pkgutil`, `codesign` are all macOS-only; this kit cannot
be executed meaningfully anywhere else. Python 3 for audit scripts. Executing model:
Cline (or similar local coding agent) with bash + filesystem access, running directly
on the machine that has the real vendor files in `build/vendor_cache/`.

## Must-Haves (Audit-Enforced)
- [ ] Every recipe parses, and the pkg recipe's `ParentRecipe` is its sibling download recipe → `bin/autopkg-preflight.py` (`recipe_parse`, `recipe_pairing`; no standalone script)
- [ ] No `PathDeleter` before anything is staged → `guardrails/audit/check_no_pathdeleter.py`
- [ ] `vendor_cache` path depth arithmetic is correct (resolves to a real, existing path) → `guardrails/audit/check_vendor_cache_path.py`
- [ ] No `%pathname%` before a step that sets it (e.g. in a `Copier`-sourced pkg recipe's `PkgCopier`/`PkgCreator` step) → `guardrails/audit/check_no_pathname_reliance.py`
- [ ] If `CodeSignatureVerifier` is present, `expected_authority_names` has the full 3-entry chain → `guardrails/audit/check_cert_chain_complete.py`
- [ ] If no `CodeSignatureVerifier`, `NO_CODE_SIGNATURE_REQUIRED: true` is explicitly declared with a comment → `guardrails/audit/check_unsigned_declared.py`
- [ ] Every `%variable%` referenced in the download+pkg pair is declared in `Input` or set by an earlier step → `guardrails/audit/check_variables_declared.py`
- [ ] Any `Copier` step copying a directory (not a single file) includes `overwrite: true` → `guardrails/audit/check_copier_overwrite.py`
- [ ] Every app directory has a `README.md` → `guardrails/audit/check_readme_exists.py`
- [ ] `manifest.sha256` exists at repo root and verifies clean against current file state → `bin/verify-manifest.sh --repo <recipe-repo>`

## Good-to-Haves (Checklist Only)
- [ ] Recipe filenames match `AppName.{download,pkg}.recipe.yaml` exactly
- [ ] Identifiers use `com.acmefruit.autopkg.{download,pkg}.AppName` (no `.pkg.download.` bug)
- [ ] `PKG_ID` values are documented as invented/not-vendor-confirmed if applicable
- [ ] The app's README records the publisher's Team ID (or says there is none)
- [ ] If the org uses the optional `.overrides` file: one holding a secret or deployment detail is generated by the pipeline or gitignored, never committed, and everything AutoPkg needs (such as `version`) is in `Input`

## Footguns
Failure modes that are subtle, destructive, or not covered by a must-have check:
- ⚠️ **AutoPkg's cache persists across separate invocations** at
  `~/Library/AutoPkg/Cache/<identifier>/`. A recipe that's genuinely fixed can still
  fail on a second run against stale cached state from a prior attempt — always
  `clear-autopkg-cache.sh` (or `bin/run-recipes.sh --clear-cache`) between
  structural changes, not just when something looks wrong.
- ⚠️ **Cloud-sync folders (OneDrive/iCloud Drive) can produce misleading
  file-visibility failures** — a file fully present to `ls`/`glob` from one process
  can still be invisible to another process's TCC grant. Costs real debugging time
  before being ruled out; default to a native local path for the working repo.
- ⚠️ **A "known-working" example recipe is only a valid template if it's the same
  pattern** — surface resemblance (same processor names) doesn't mean same
  mechanism. Verify which of the 5 patterns it actually is before copying its shape.
- ⚠️ **Silent handoff drift is a bigger time-sink than any individual recipe bug.**
  Never trust "I think this file landed correctly" — `verify-manifest.sh` before
  running anything, every time, no exceptions for "it's a small change."

## Known Constraints / Standards
- `recipes/VendorName/AppName/` layout, mirrored exactly by `build/vendor_cache/VendorName/AppName/`
- Per-app `README.md` documents pattern choice + rationale + any bugs found/fixed for that app
- Static (unversioned) `Acme_AppName.pkg` output naming
